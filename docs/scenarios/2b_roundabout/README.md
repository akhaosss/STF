本文说明国标场景、仓库数据和判定字段之间的对应关系。实际使用入口如下：

- 已有场景直接运行：[直接运行已有2.b场景](run_existing.md)；
- 修改路线、天气或车型：[编辑与场景扩展](startup.md)；
- 字段、单位和结果目录：[参数、证据与结果目录](results_and_parameters.md)；
- 首次部署：[环境安装与验证](../../environment_setup.md)。

## 1. 国标场景定义

本节依据GB/T 41798—2022第6.2.2条整理。仓库中的门线、距离、时序和容差属于仿真实现，不应作为标准原始参数引用。

### 1.1 试验道路与目标车

- 环形路口包含不少于3个物理接入方向。
- 每个接入方向至少有一条进口车道和一条出口车道。这里的“双向两车道”不要求环岛内部必须为双车道。
- VUT驶入环岛所用入口的上游存在一辆行驶目标车辆VT1。
- 从VUT入口开始沿环流方向遇到的下游第1个车辆入口存在一辆静止目标车辆VT2。

本文使用以下术语：

- **物理接入方向（arm）**：属于同一接入道路体系的一组进口和出口车道。中央分隔带导致进口和出口错开时，仍可属于同一个arm。
- **VUT汇入口**：VUT从接入道路进口车道进入环形行车道的位置。
- **出口1/2/3**：从VUT汇入口开始，沿环流方向依次遇到的第1、第2、第3个出口车道口。
- **下游第1入口**：从VUT汇入口开始，沿环流方向遇到的下一个进口车道口。

出口1描述VT1驶出的车道口，下游第1入口描述VT2所在的进口车道口，二者不是同一概念。在进出口错位的arm上，程序分别按实际进口和出口门线排序。

### 1.2 试验方法

- VUT沿当前车道驶向环岛，规划从出口2或出口3驶出。
- VUT到达环岛入口时，VT1仍位于入口上游。
- VT1以15 km/h匀速行驶，并从出口1驶出。
- VT2保持静止。

本条没有规定VUT入口前速度、环岛直径、环岛内部车道数量、车辆间距/TTC、VT2距入口的精确距离和入口判定平面。仓库在`roundabout_test.engineering`中保存这些仿真参数。

### 1.3 通过要求

不具备环岛行驶功能时，VUT应在进入前给出超出设计运行范围提示，且不得进入环岛。

具备环岛行驶功能时，应同时满足：

- 从规划出口驶出并进入对应车道；
- 不与VT1、VT2碰撞；
- 进入环岛后不紧急制动或停车。

项目还记录通用判定证据，包括实线骑轧、限速、行驶方向、转向灯和道路基础设施碰撞。仿真证据范围见[参数、证据与结果目录](results_and_parameters.md#4-仿真证据配置)。

## 2. 仓库发布的数据

可运行场景位于：

```text
save_scenarios/2b/definitions/
```

当前数据集包含一条已审核路线的960个condition：120种天气与8组VT1/VT2车型的笛卡尔积。每个JSON都包含完整的VUT/VT1路线、VT2位置、拓扑、门线、天气、车型和工程参数，可脱离编辑器直接运行。

数据模型为：

- VUT：`ego_start`与`ego_route`；
- VT1：角色为`vt1`的目标车、起点和路线，目标速度固定为15 km/h；
- VT2：角色为`vt2`的静止目标车，不设置路线；
- 专项配置：`roundabout_test`；
- 完整清单：`2b_scenario_manifest.json`。

地图拓扑缓存`config/roundabout_topology/`用于编辑器复核，不是运行已有JSON的依赖。场景JSON已经保存本次运行所需的拓扑和门线。

## 3. 国标要求与仓库字段

| 国标要求或概念 | 仓库表示 | 证据或判定 |
|---|---|---|
| 不少于3个接入方向 | `topology.arm_count >= 3` | 保存前校验拓扑和各arm车道数 |
| 每个方向至少一进一出 | `topology.arms[].inbound_lane_count/outbound_lane_count` | 任一方向不完整则配置无效 |
| VUT驶向环岛 | `ego_start`、`ego_route`、`entry_gate` | 路线连通和入口门线穿越 |
| VUT从出口2或3驶出 | `roundabout_test.planned_exit` | 出口门线、对应车道和路线完成 |
| VT1位于入口上游 | VT1起点和工程距离字段 | 建场及入口事件检查 |
| VT1保持15 km/h | `vt1.target_speed_kmh = 15.0` | 稳速窗口和逐帧速度记录 |
| VT1从出口1驶出 | `vt1.exit_number = 1` | 观测VT1实际通过出口1门线 |
| VT2位于下游第1入口 | `downstream_entry`和VT2车道信息 | 位置、连通性和静止状态 |
| 不具备功能时提示且不进入 | `roundabout_capable=false` | 入口前ODD/HMI提示和门线状态 |
| 具备功能时正确驶出 | `roundabout_capable=true` | 出口、车道、碰撞、停车和急刹判定 |
| 通用道路要求 | 限速、lane invasion、方向、灯光和碰撞事件 | `events.json`与`summary.json` |

该表说明仓库如何表达和采集要求，不代表一次仿真运行即可替代物理场地认证。

## 4. 用户设置与程序生成

修改路线时，用户需要确认：

- 测试能力分支；
- 环岛各物理arm的进口和出口车道；
- VUT起点及从出口2或3驶出的路线；
- VT1在环形车道上的起点及从出口1驶出的路线；
- VT2在下游第1入口进口车道上的静止位置。

程序负责：

- 根据CARLA有向车道图补全VUT和VT1开放路线；
- 识别VUT汇入口、出口编号和下游第1入口；
- 生成有方向的有限宽度门线；
- 计算VT1布置和放行时序，使VT1按设定时间差先经过共同冲突区域；
- 控制VT1保持15 km/h并令VT2驻车；
- 按YAML扩展天气和VT1/VT2车型；
- 记录逐帧遥测、事件、视频和判定摘要。

路线补全使用局部有界A*车道图搜索，搜索前向分支和OpenDRIVE允许的同向变道，不要求把VUT路线拟合成圆，也不要求VUT绕行一周。具体按键、颜色和推荐路点间隔见[编辑与场景扩展](startup.md)。

## 5. 运行定位

仓库提供的`behavior`实际调用`EgoRouteFollowScene.follow_route`，用于展示场景加载、控制接口、证据采集和结果输出。它不是CARLA官方`BehaviorAgent`，也不是乙方必须采用的ADS。

TCP代码是另一个可选接入示例。场景数据与控制器解耦，不要求使用者依次运行Behavior和TCP。直接运行参考示例的方法见[直接运行已有2.b场景](run_existing.md)；接入其他ADS时应保留相同的场景配置和证据字段。

若测试计划要求同一condition重复3次，运行器可以生成trial 1/2/3并分别聚合；如果只是数据联调或场景筛选，可以每个condition运行一次。重复次数和ADS组合由具体测试计划决定，不由编辑器强制。

## 6. 现场确认范围

纯Python测试覆盖配置校验、重复条件一致性和结果聚合。以下内容依赖目标CARLA地图和运行环境，发布或换图后仍需现场检查：

- OpenDRIVE车道和junction连通关系；
- 入口、出口门线位置和方向；
- 多车道接入方向的拓扑展开；
- 目标ADS的实际控制效果；
- 地图限速、实线和导向标线证据是否可用。

这些检查不会改变发布JSON中的天气、车型和路线指纹。
